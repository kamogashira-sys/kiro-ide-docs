# 公式情報源の一覧と使い分け

**本サイトが根拠にしている情報源を、性質・信頼度・使いどころの順に整理します。**

「どのページに何が書いてあるか」は [01_official-site-structure.md](01_official-site-structure.md) を参照してください。本ページは「**どの情報源をどこまで信じるか**」を扱います。

---

## 📊 情報源の一覧

| 順位 | 情報源 | URL | 内容 | 主な用途 |
|-----|-------|-----|------|---------|
| **1** | **公式 changelog ページ（HTML）** | <https://kiro.dev/changelog/ide/> | リリースノート本体 | **リリース内容・日付の正** |
| **2** | **ドキュメントの `.md` 版** | 各ページ＋`.md` | 本文のプレーン Markdown | 機能仕様・表記の確認 |
| **3** | **公式ドキュメント索引** | <https://kiro.dev/llms.txt> | 全ドキュメントページの `.md` URL と説明文 | 新規ページの検知・IDE/CLI 共有の判定 |
| **4** | **サイトマップ** | <https://kiro.dev/sitemap.xml> | 全 463 URL | ページ全量の棚卸し |
| **5** | **Atom / RSS フィード** | <https://kiro.dev/changelog/feed.atom> | 直近25件のリリース | **新リリースの速報検知のみ** |
| 6 | IDE 実機 | — | 実際の画面・挙動 | 公式記述の解像度を上げる用途に限る |
| 7 | 公式ブログ | <https://kiro.dev/blog/> | 技術記事・事例 | 参考。仕様の根拠にはしない |
| — | GitHub Issues | <https://github.com/kirodotdev/Kiro> | 不具合報告・要望 | **一次情報ではない**（未修正の報告・推測が混在） |

**順位の使い方**:

- 順位1・2で確認できない事項は「**未確認**」と明示し、断定して掲載しません
- `.md` 版と HTML で内容が食い違う場合は **HTML を優先**します（食い違いの実例は §1.2）
- **フィードだけを根拠にしません**（理由は §3）
- **Kiro CLI 版のドキュメントは Kiro IDE の一次情報ではありません**（同名機能でも仕様が違う。[README.md](README.md#-ide-と-cli-を混同しないために) 参照）

## 1. `llms.txt` — 公式が用意した機械可読の索引

LLM に読ませることを想定した索引で、**全ドキュメントページの `.md` URL と1行説明**が並んでいます（31.8 KB・**203 URL**）。

冒頭の説明:

> Each URL below has a plain-Markdown companion at the same path with a `.md` suffix (e.g. `/docs/chat` → `/docs/chat.md`).

5つのセクションに分かれます。

| セクション | URL 数 | 内容 |
|-----------|-------|------|
| `## IDE` | 64 | Kiro IDE 固有 |
| `## CLI` | 66 | Kiro CLI 固有 |
| `## Web` | 20 | Kiro Web 固有 |
| **`## Shared`** | **31** | **IDE と CLI の両ツリーから読めるページ**（内容は同一） |
| `## Optional` | 22 | チュートリアル・課金の詳細手順・トラブルシューティング |

**`## Shared` の価値**: IDE 版として書くべき範囲と CLI に委ねる範囲の境界を、推測ではなく公式の分類で引けます。本サイトが「この機能は IDE/CLI 共有」と書いている箇所の根拠はここです。

**`sitemap.xml` との差（実測）**: sitemap のドキュメント 238 URL に対し、`llms.txt` に載るのは 203 です。差の **35 URL はすべて `/docs/cli/` 配下の共有ページのミラー**でした（`/docs/cli/billing` など。`Shared` セクションが IDE 側の URL だけを列挙しているため）。**IDE ツリーの 117 ページはすべて `llms.txt` に載っています**。

### 1.2 `.md` 版が HTML と食い違う2つのケース（実測）

`.md` 版は便利ですが、**HTML の表示内容と完全に一致するわけではありません**。実測で見つかった2種類の欠落を挙げます。どちらも「`.md` を読んだだけでは誤った記述をしてしまう」類のものです。

**ケース1: プレースホルダが消える**

`/docs/enterprise/managed-updates` のマニフェストパスの表を比べます。

| 版 | 表示内容 |
|----|---------|
| HTML | `{base}/{quality}/metadata-darwin-{arch}-{quality}.json` |
| **`.md`** | `//metadata-darwin--.json` |

`{base}`・`{quality}`・`{arch}` といった波かっこ付きのプレースホルダが**すべて空文字に置き換わっています**。`.md` だけを読むと、パスの構造そのものが読み取れません。同じページの説明文も「`` is `x64` or `arm64`」のように主語が消えています。

**ケース2: 共有ページで3サーフェス分の内容が連結される**

`/docs/privacy-and-security/firewalls` は IDE/CLI/Web 共有ページで、HTML は**アクセスした URL ツリーに応じた内容だけ**を描画します。ところが `.md` 版は3サーフェス分をすべて連結して出力します。

| 版 | 内容 |
|----|-----|
| HTML（`/docs/...`） | IDE 向けのみ。「Traffic type」列は全行が `IDE` |
| HTML（`/docs/cli/...`） | CLI 向けのみ |
| **`.md`** | **IDE・CLI・Web の3つ分**。同じ見出し（`Optional URLs`・`Proxy configuration`・`Data perimeters`）が2回ずつ現れ、「Traffic type」列は `IDE / CLI` になる |

さらに、IDE 版の HTML には「Wildcard rules」の節が**存在しません**（Web 版にのみ存在）。にもかかわらず IDE 版の本文には `#wildcard-rules` へのリンクがあり、**リンク先が同じページ内に無い**状態です。`.md` を読むと Wildcard rules が IDE でも使えるように見えます。

**したがって**: 共有ページを扱うときは、**必ず IDE ツリーの URL（`/docs/...`）の HTML を見て判断**します。`.md` は下書きの材料としてのみ使い、表の値やパスの形式は HTML で確認します。

## 2. `sitemap.xml` — ページ全量の棚卸し

463 URL の一覧です。用途は次の3つ:

1. **ページ数の実測**（本サイトの件数はすべてここから機械集計）
2. **新規ページの検知**（前回取得分との差分）
3. **`llms.txt` の網羅性の検証**（§1 の差の確認）

**取得と集計の例**:

```bash
curl -sS -A "Mozilla/5.0" https://kiro.dev/sitemap.xml -o sitemap.xml
grep -oP '(?<=<loc>)[^<]+' sitemap.xml | grep -c '/changelog/ide/'
```

## 3. Atom / RSS フィード — 速報検知にだけ使う

| 項目 | 実測値 |
|------|-------|
| URL | <https://kiro.dev/changelog/feed.atom>（RSS 版: <https://kiro.dev/changelog/feed.rss>） |
| エントリ数 | **25 件固定**（ローリングウィンドウ） |
| 内容 | 全サーフェス混載。IDE 15 / CLI 7 / Models 2 / General 1 |
| サーフェスの判定 | Atom は `<category term="IDE"/>`、RSS は `<category>IDE</category>` |
| Atom と RSS の関係 | **同じ25件・同じ順序**。項目の構造が違うだけ |

### 3.1 フィード単独では網羅できない（実例）

**1.0.165（2026-07-16）はフィードに存在しません。** 25件のウィンドウから押し出されたためです。フィードだけを情報源にしていれば、このバージョンは本サイトから丸ごと欠落していました。

**同じバージョンが2エントリで配信される**という性質もあります。

| リンク | 意味 |
|-------|------|
| `https://kiro.dev/changelog/ide/1-0-242` | 専用ページ |
| `https://kiro.dev/changelog/ide/1-0#patch-1-0-242` | 系列ページ内のアンカー |

そのため IDE の15エントリは実際には **9バージョン**しか表していません。重複を正規化しないと版数を数え間違えます。

### 3.2 新バージョン検知は3情報源の和集合で行う

| 情報源 | 得られるもの | 単独では足りない理由 |
|-------|------------|-------------------|
| **フィード** | 直近の速報 | 25件のウィンドウで取り落ちる（1.0.165）。重複配信もある |
| **系列ページの埋め込みパッチ索引** | その系列の全パッチ | **新しい系列そのものは知れない**（`/changelog/ide/1-1/` が生まれても気づけない） |
| **`sitemap.xml`** | 新規 URL の出現 | **日付が取れない**。パッチはアンカーなので URL が増えない |

3つを突き合わせることで、どれか1つの弱点を他の2つが埋めます。

## 4. Changelog 本文の取り方（つまずきどころ）

changelog は本サイトで最も分量の多い部分なので、取得方法を具体的に記します。

### 4.1 `.md` 版は存在しない

| 対象 | `.md` 版 |
|------|---------|
| ドキュメント | ✅ 全ページに存在（`/docs/chat.md`） |
| **Changelog** | ❌ **404**（`/changelog/ide/1-0-242.md`） |

そのため **HTML から読むしかありません**。

### 4.2 HTML を叩くときの2つの罠

| # | 現象 | 対処 |
|---|------|------|
| 1 | 末尾スラッシュなしは **301 リダイレクト**（本文が返らない） | 末尾スラッシュを付ける、または `curl -L` |
| 2 | User-Agent が**空文字**だと **403**（`Request blocked.`） | User-Agent を送る（`curl` の既定 UA でも 200） |

```bash
# 末尾スラッシュあり・User-Agent 付き
curl -sSL -A "Mozilla/5.0" -o 1-0.html "https://kiro.dev/changelog/ide/1-0/"
```

### 4.3 本文は可視 HTML には入っていない

公式サイトは Next.js で構築されており、**changelog の本文は可視 HTML ではなく `self.__next_f.push([1,"..."])` というスクリプト断片の連なり**に入っています。さらに Improvements / Fixes は**アコーディオン内でクライアント側が描画する**ため、HTML をそのまま読んでも現れません。

本文の全量を得るには、このスクリプト断片を復元する必要があります。

### 4.4 「パッチ一覧」は索引であって本文ではない

系列ページには次の形のデータが埋め込まれています。

```
"patches":[{"id":"patch-1-0-242","version":"1.0.242","date":"Jul 28, 2026"}, ...]
```

これはページ左の「**Latest Patches**」ナビゲーションのための**索引**で、構造上 `version` と `date` しか持ちません。

**パッチの説明文は本文側の別ノード**にあります。索引と同じ `id` を持つ `<div id="patch-1-0-242">` がそれで、そこに `**1.0.242** | Jul 28, 2026` という見出しと箇条書きが入っています。

| 用途 | 見るべき場所 |
|------|------------|
| **パッチの網羅性**（何件あるか・取り落ちがないか） | **索引**（`"patches"` 配列） |
| **記述内容**（説明があるか・何が書かれているか） | **本文ノード**（`id="patch-*"` の div） |

**索引に説明が無いことを「説明が存在しない」と読み替えないでください。** 実測では **45パッチすべてに説明が存在**します（うち15件は Improvements/Fixes の節を持ち、0.8.135 は9グループ33項目）。

なお `"patches"` 索引は**系列ランディングページにしか存在しません**。リリース専用ページ（`1-0-242` など）と 0.2 系の4ページには 0 件です。

## 5. 日付の扱い

| 項目 | ルール |
|------|-------|
| **正** | **公式ページの表示日**（埋め込みデータの `date`。例: `Jul 28, 2026`） |
| 表記 | **ISO 形式 `YYYY-MM-DD`** に変換して掲載 |
| タイムゾーン | **変換しない** |
| 取得日 | **本文には書かない**（作業記録側に残す） |

**タイムゾーン変換をしない理由**: フィードの `published` とページ表示日を全件照合したところ、**日付は全件一致し、差があるのは時刻だけ**でした（系列ページのパッチは `00:00Z` 固定、専用ページは実時刻）。時刻をもとに日付をずらすと、公式表示と食い違うだけです。

**系列ランディングページの日付に注意**: `/changelog/ide/1-0/` に表示される日付は**その系列の初出日**（1.0 なら 2026-06-25）であり、系列内の最新ビルドの日付ではありません。

## 6. 本サイトの検証の考え方

本サイトは記述の正しさを人間の目視だけに任せず、機械チェックを併走させています。

| 検証の種類 | 何を見るか | 限界 |
|-----------|----------|------|
| **文書内部の整合** | リンク・アンカーの実在、日付書式、バージョンの降順、記述粒度 | **公式にあるのに書き忘れた記述は検出できない** |
| **一次情報との突き合わせ** | 公式の全バージョンが掲載されているか、日付が一致するか、説明が転記されているか | 一次情報のスナップショットが必要 |

前者だけでは「バージョンを1件まるごと書き忘れた」ケースを検出できません。そのため後者を別に用意し、公式ページから抽出した結果と本サイトの記述を突き合わせています。

## 7. 監視が必要な事項（今後変わりうる点）

| # | 項目 | 変化したときの影響 |
|---|------|-----------------|
| 1 | `.md` 版の欠落（§1.2 の2ケース）が修正されるか・増えないか | 増えると順位2をさらに慎重に扱う必要がある |
| 2 | 埋め込みパッチ索引の構造 | Next.js の内部形式なのでサイト改修で変わり得る。網羅性の担保手段を失う |
| 3 | フィードのウィンドウ長（25件は実測値） | 短くなると取り落ちの頻度が上がる |
| 4 | ショートカット公式ページの件数（現在29件） | 本サイトの記載数を更新する必要がある |
