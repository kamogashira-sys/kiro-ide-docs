## 2. モデルの切り替え方

チャット画面の**モデルドロップダウン**で切り替えます。選択は**その会話の以降のメッセージすべてに適用**されます。

> 一覧にあるモデルがドロップダウンに現れない場合は、クライアントを再起動すると解決します。

## 3. どのモデルを使うか（公式の対応表）

| 用途 | モデル | 理由（公式） |
|------|-------|-----------|
| **一般的な開発** | **`Auto`** | 作業ごとに最適なモデルへ振り分け、品質とコストを自動で釣り合わせる |
| 最も難しい多段階の開発 | **GPT-5.6 Sol** | 長期的なリファクタや、持続的な計画とツール連携が必要なターミナル作業に最適 |
| 日常的な多段階の開発 | GPT-5.6 Terra | エージェント作業のバランス帯。1.2x は Luna の 0.6x と Sol の 2.4x の中間 |
| 高頻度のエージェント作業 | GPT-5.6 Luna | GPT-5.6 で最速・最低コストの帯。スループットが重要な繰り返し作業に |
| **最高の信頼性** | **Opus 5** | エージェントコーディングのベンチマークで最高水準。マルチエージェント連携が最も強く、**スタブを残さず作業を完遂する** |
| 低コストで Opus に近い動き | Sonnet 5 | 推論とツール利用で Opus 4.8 に迫る。編集前に計画し、より長く自律的に動く |
| 速度・クレジット節約 | Haiku 4.5 | 一部のコストでフロンティアに近い知性。素早い反復とサブエージェント向き |
| 低コストでフロンティア級 | MiniMax M2.5 | 0.25x のコストで Opus 級に近い結果。開発ライフサイクル全体で強い |
| リポジトリ規模の作業 | GLM-5 | 大規模コードベースを横断する長期ワークフロー向けに最適化された 200K コンテキスト |
| 予算内で長いコーディング | Qwen3 Coder Next | 0.05x のコストで 256K コンテキスト。エラー回復が強い |

### 3.1 公式のベストプラクティス

| 指針 |
|------|
| **まず `Auto` から始める**（ほとんどの作業で。品質とコストを自動で最適化） |
| 最も難しい多段階作業には **GPT-5.6 Sol** |
| スループットやコストを優先するなら **GPT-5.6 Terra（バランス）または Luna（最大効率）** |
| **複雑な問題で行き詰まったら Opus 5 に切り替える**（持続的な複数ファイル作業・最強のマルチエージェント連携とコードレビュー精度） |
| Opus より低コストで強いエージェント動作が欲しいなら **Sonnet 5**（完遂が必要な多段階作業） |
| 素早い反復・単純な修正・クレジット節約には **Haiku** |
| **アカウント設定で使用量を監視する**（モデル選択が消費にどう影響するか把握する） |
| **モデルのコストをプランに織り込む**（主に Opus を使うなら Pro+・Pro Max・Power を検討） |

## 4. `Auto`（モデルルーター）の挙動

`Auto` は Kiro のモデルルーターです。複数のフロンティアモデルと最適化技術を組み合わせ、作業ごとに最適なモデルを自動で選びます。

| プラン | 品質の目安 |
|-------|----------|
| Free | **Claude Sonnet 4.5 相当以上** |
| 有料 | **Claude Opus 4.6 相当以上**（トラフィック振り分けも強化される） |

### 4.1 管理者が注意すべき点（重要）

`Auto` はモデルガバナンス上、**独立した選択肢として扱われます**。管理者は `Auto` を許可/禁止できます。

> **ただし `Auto` を有効にした場合、内部の振り分けは管理者が承認したモデルに限定されません。**
> そのリージョンで一般提供されているどのモデルにも振り分けられる可能性があります。

`Auto` は **experimental のモデルには振り分けません**。

**承認したモデルだけで処理させたい組織は、`Auto` を禁止し、承認済みモデルを既定に設定する**必要があります（ガバナンス設定は [03_deployment/04_enterprise.md](../03_deployment/04_enterprise.md)）。

## 5. 推論の深さ（Reasoning effort）

対応するモデルでは、**プロンプトに対してどれだけ推論を費やすかを制御できます**。低い水準は速く短い応答でクレジット消費も少なく、高い水準はより多くのトークンを深い分析・多段階の推論・丁寧なコード生成に使います。

### 5.1 設定方法（IDE）

> 出典: [Reasoning effort](https://kiro.dev/docs/models/effort/)（公式ページ更新日: 2026-10-09）の IDE の記述・[1.2.37](../02_update/01_changelog.md#v1-2-37)・[1.2.56](../02_update/01_changelog.md#v1-2-56)

1. チャット入力バーの**モデルボタン**をクリックして、Model パネルを開きます。必要なら **Filter models** で絞り込み、モデルまたは `Auto` を選びます
2. 選んだモデルが推論の深さに対応しているときは、モデルの一覧の下に **Effort** のスライダーが現れます。スライダーで水準を選ぶと、**次のメッセージから、その会話の以降のメッセージすべてに適用**されます
3. モデルの既定の水準に戻すには、**`Default: <水準>`** のリセット操作を選びます。この操作は、別の水準ではありません

- **ローカルセッションで、最初のメッセージを送る前に** Effort（モデルが対応していれば Thinking も）を設定でき、セッションが始まった後もその選択は保たれます（[1.2.56](../02_update/01_changelog.md#v1-2-56)）
- モデルボタンに表示されるのは、選んだモデルまたは `Auto` で、**水準は表示されません**。ボタンにカーソルを合わせると、ツールチップに現在のモデルと水準が表示されます
- **IDE の Effort の操作が現れるのはローカルセッションだけです**。Agent Focus Mode の新しいセッションの下書きとクラウドセッションには表示されません
- 1.2.37 で、モデルの検索と Effort の操作が **1 つのパネル**にまとまりました（[1.2.37](../02_update/01_changelog.md#v1-2-37)）

> **公式ページの記述が変わった点**: 以前の本ページは、モデルセレクタの「右側の **Effort** パネル」で水準を選び、選んだ水準が「モデル名の隣に表示される（例: `Claude Opus 4.6 · Max`）」と書いていました。現行の Reasoning effort ページ（公式ページ更新日: 2026-10-09）は、上の 1〜3 のとおり、モデルの一覧の下の Effort スライダーで選び、モデルボタンには水準を表示しないと説明しています。

| 水準 | 挙動 |
|------|------|
| **Low** | 速く簡潔な応答。単純な質問や素早い確認向き |
| **Medium** | バランスの取れた推論。ほとんどの開発作業に適する |
| **High** | 丁寧な分析。複雑なリファクタリングや設計判断に向く |
| **XHigh** | 拡張された推論。複数ファイルの変更や込み入った問題に有用 |
| **Max** | 最大の深さ。難しいデバッグ・セキュリティ分析・複雑なロジックに最適 |

### 5.2 モデルごとに使える水準

**セレクタには現在のモデルで使える水準だけが表示されます。**

| モデル | 使える水準 |
|-------|----------|
| Claude Opus 5 | Low / Medium / High / **XHigh** / Max |
| Claude Opus 4.8 | Low / Medium / High / **XHigh** / Max |
| Claude Opus 4.7 | Low / Medium / High / **XHigh** / Max |
| Claude Opus 4.6 | Low / Medium / High / Max（**XHigh なし**） |
| Claude Sonnet 5 | Low / Medium / High / **XHigh** / Max |
| Claude Sonnet 4.6 | Low / Medium / High / Max（**XHigh なし**） |
| GPT-5.6 Sol・Terra・Luna | `none` / Low / Medium / High / **XHigh** / Max（公式は GPT-5.6 の既定を `high` と説明） |
| Claude Sonnet 5.5 | Low / Medium / High / **XHigh** / Max（下の注記を参照） |

> ⚠️ **公式の記述に食い違いがあります。** 公式 Reasoning effort ページ（2026-10-09）は、同じページの中で Claude Sonnet 5.5 の Effort を2通りに書いています。「Reasoning configuration examples」の表は `low`・`medium`・`high`・`xhigh`・`max` の5水準を載せ、`thinking.type` の説明は Sonnet 5.5 が `low`・`medium`・`high` の Effort に対応するとしています。**読み方**: どちらが現行の仕様かは公式に記載がなく、**未確認**です。実際に選べる水準はモデルピッカーと Effort の操作で確認してください。

この表は、公式 Reasoning effort ページ（公式ページ更新日: 2026-10-09）の「Reasoning configuration examples」を、IDE の水準の名前に直したものです。公式は、この例を**設定スキーマの代表例であって、対応モデルの網羅ではない**と書いており、実際に使えるモデルと水準はモデルピッカーと Effort の操作で確認するよう案内しています。Claude Sonnet 5.5 は、本ページ第1節の表にないモデルです（上の注記）。上の表に載っていないモデルの対応は、公式ページに記載がありません（**未確認**）。

モデルの設定スキーマが内部の `default` 水準だけを宣言している場合は、選べる水準がないため、ピッカーそのものが表示されません（公式）。

### 5.3 調整の目安（公式）

| 場面 | 操作 |
|------|------|
| エージェントの答えが浅い・エッジケースを見落とす・実装が不完全 | **上げる** |
| 素早い答えが欲しく、長い推論を待ちたくない | **下げる** |
| セキュリティレビュー・複雑なデバッグ・多数の制約が絡む場合 | **最高水準を使う** |

> **高い水準は内部で多くのトークンを使うため、同じ Cost でもクレジット消費が増えます。**
> これが「同じ倍率の2つのモデルで同じ作業のコストが変わる」理由の1つです。

## 6. モデルのライフサイクル

Kiro のモデルは2つの段階を経ます。

| 段階 | 内容 |
|------|------|
| **Experimental** | 早期テスト向けで、フィードバックに応じて変わりうる。モデルセレクタに印が付き、**利用できるリージョンが限られる** |
| **Active** | 完全にサポートされ、本番利用が推奨される。**すべての対応リージョンで利用できる** |

> **Experimental のモデルは、可用性と性能の最適化のために世界中の複数の AWS リージョンで処理される可能性があります。**
> 処理場所に制約がある組織では注意が必要です（[03_deployment/05_security.md](../03_deployment/05_security.md) §5.3）。

## 8. モデルのフォールバック通知（1.3.0 で追加）

> 出典: [Models](https://kiro.dev/docs/models/#model-fallback-notices) の「Model fallback notices」節（公式ページ更新日: 2026-10-24）・[1.3.0](../02_update/01_changelog.md#v1-3-0)

現行のモデルが依頼を断る、または利用できないとき、Kiro は 1 つのターンを別のモデルに移すことがあります。**トランスクリプトに、継続したモデルの名前と、その変更が 1 ターンだけか、会話の残り全体に適用されるかが表示されます。**

- IDE では、**サブエージェント内で起きたフォールバックは、そのサブエージェントのアクティビティ内に表示**されます
- 同じモデルのままで再試行したときは、**一時的な再試行の通知**として表示されます
- **1.4.26 の修正**: Auto モデルが応答を再試行するとき、再試行の通知は、モデル名ではなく「Couldn't complete this response. Retrying…」と表示されます（[1.4.26](../02_update/01_changelog.md#v1-4-26)）

公式はこの動作を「ローカルの V3 セッション」の説明として書いています。IDE のどの条件がこれに当たるかは、公式の記述を確認できていません（**未確認**）。Kiro CLI での表示（試したモデルと結果の一覧）は公式の別ページの説明で、本サイトでは扱いません。
