# Specs（仕様駆動開発）

**アイデアを「要件・設計・タスク」という3つの成果物に落として実装する、Kiro の中核機能です。**

- **一次情報**: [Specs](https://kiro.dev/docs/specs/)（公式ページ更新日: 2026-07-22）・[Feature Specs](https://kiro.dev/docs/specs/feature-specs/)・[Quick Spec](https://kiro.dev/docs/specs/quick-spec/)・[Analyze Requirements](https://kiro.dev/docs/specs/analyze-requirements/)・[Bugfix Specs](https://kiro.dev/docs/specs/bugfix-specs/)・[Correctness](https://kiro.dev/docs/specs/correctness/)
- **ファイルの置き場所**: [04_reference/01_kiro-directory.md](../04_reference/01_kiro-directory.md#3-仕様specs--kirospecs機能名)

> **これは何か**: spec（仕様）は、機能追加やバグ修正の開発プロセスを**形式化した成果物**です。
> 「高レベルのアイデア」を「追跡可能な詳細な実装計画」に変換します。

---

## 1. 3つの成果物

どの spec でも次の3ファイルが生成され、`.kiro/specs/<機能名>/` に保存されます。

| ファイル | 内容 |
|---------|------|
| **`requirements.md`**（バグ修正では **`bugfix.md`**） | ユーザーストーリー・受け入れ基準、またはバグの分析を構造化した記法で記述 |
| **`design.md`** | 技術アーキテクチャ・シーケンス図・実装上の考慮事項 |
| **`tasks.md`** | 個別に追跡可能なタスクに分けた詳細な実装計画 |

公式が挙げる spec でできること:

- **要件を分解する**（受け入れ基準付きのユーザーストーリーへ）
- **設計文書を作る**（シーケンス図とアーキテクチャ計画付き）
- **実装の進捗を追う**（個別のタスク単位で）
- **効果的に協業する**（プロダクトとエンジニアリングの間で）

---

## 2. 3フェーズのワークフロー

すべての spec は同じ3段階を通ります。

| 段階 | 成果物 | 内容 |
|------|-------|------|
| **1. 要件 / バグ分析** | `requirements.md` / `bugfix.md` | 何を作る（直す）かを定める |
| **2. 設計** | `design.md` | システムアーキテクチャ・コンポーネント設計・シーケンス図とデータフロー・エラー処理とテスト戦略 |
| **3. タスク** | `tasks.md` | 実行可能な個別タスクに分解する |

---

## 3. spec の種類（2つ）

| 種類 | 用途 | 最初の成果物 |
|------|------|------------|
| **Feature Specs** | 新機能・新しい能力の追加 | `requirements.md` または `design.md`（下記の2つの流れ） |
| **Bugfix Specs** | バグの診断と修正（リグレッションを防ぎながら） | `bugfix.md` |

### 3.1 Feature Specs の2つの流れ

**出発点が要件なのか設計なのかで選びます。**

| 流れ | 順序 | こんなときに使う |
|------|------|--------------|
| **Requirements-First** | 要件 → 設計 → タスク | ・作りたいシステムの**振る舞いが分かっている**<br>・アーキテクチャは柔軟で、ニーズに合わせて設計できる<br>・顧客フィードバック起点の製品機能を作る<br>・技術的制約のないグリーンフィールドの立ち上げ<br>・プロダクト主導の組織で働いている |
| **Design-First** | 設計 → 要件 → タスク | ・**アーキテクチャが頭にある**（高レベル設計）<br>・疑似コードやアルゴリズムから実装の振る舞いを始めたい（低レベル設計）<br>・**厳しい非機能要件**（レイテンシ・スループット・コンプライアンス）を満たす必要がある<br>・他ツールの設計文書を Kiro に持ち込む<br>・スコープを固める前に技術的な実現可能性を探る |

**どちらの流れでも、各成果物には承認ゲートがあります。** 納得できなければ編集・変更依頼をして作り直し、納得したら次の段階に進みます。

### 3.2 Feature Specs が向く場面

| 向く | 向かない |
|------|---------|
| ・構造化された計画が必要な複雑な機能<br>・実装タスクが複数ある機能<br>・チーム協業のための文書が必要なプロジェクト<br>・要件や設計を繰り返し練る必要がある機能 | ・**バグ修正**（Bugfix Specs を使う）<br>・目標が明確でない探索的なコーディング |

### 3.3 Bugfix Specs の書き方（3つの振る舞い）

Bugfix Specs は**経験のある開発者のバグ修正の進め方**をモデルにしています。根本原因を特定し、何を変えるべきかを理解し、**変えてはいけないものを明示的に保護します**。

`bugfix.md` には3種類の振る舞いを書きます。

| 区分 | 記法 |
|------|-----|
| **現在の振る舞い（欠陥）** | WHEN [条件] THEN the system [誤った振る舞い] |
| **期待する振る舞い（正しい状態）** | WHEN [条件] THEN the system SHALL [正しい振る舞い] |
| **変えない振る舞い（リグレッション防止）** | WHEN [条件] THEN the system SHALL **CONTINUE TO** [既存の振る舞い] |

**この構造によって、Kiro は「何が壊れているか」だけでなく「何が動き続けなければならないか」を理解します。**

**向く場面**: 根本原因の分析が必要な複雑なバグ／リグレッションのコストが高い重要な経路のバグ／コンプライアンスやチームの知識のために文書化が必要なバグ／**過去の修正がリグレッションを起こしたことがある**場面。

## 4. Quick Spec（承認ゲートなしで一気に作る）

**セッションモードの1つ**で、要件・設計・タスクを**1回で自動生成**します。各段階を承認する代わりに、**最初にまとめて明確化の質問に答えます**。

| 順 | 内容 |
|----|------|
| 1 | Kiro ペインの **Specs** の `+` を押す（またはチャットペインで **Spec** を選ぶ） |
| 2 | セッション種別の選択で **Quick Spec** を選ぶ（Feature Specs・Bugfix Specs と並んでいる） |
| 3 | **Kiro が最初に明確化の質問をする**（スコープ・制約・エッジケースなど、出力に影響するもの） |
| 4 | 回答をもとに `requirements.md`・`design.md`・`tasks.md` を順に自動生成する（**承認ゲートなし**） |
| 5 | タスク一覧に到達する |

**明確化の質問が鍵になる相互作用点**です。各成果物をレビュー・承認する代わりに、**入力を前倒し**して Kiro が自律的に質の高い spec を作れるようにします。

### 4.1 使い分け

| 状況 | 選ぶもの |
|------|--------|
| **よく理解している機能**（Kiro の出力を信頼でき、要件や設計を練る必要がない） | **Quick Spec** |
| **素早いプロトタイピング**（レビューより速度が重要） | **Quick Spec** |
| 不慣れな領域を探索している／要件を練る必要がある／レビューゲートがチームにとって本当に価値がある | **標準の Feature Specs** |

公式の判断指針: 要件の質が重要な機能（**コンプライアンスに関わる領域・重大なシステム・不慣れな領域**）では標準の Feature Specs が適します。何度も作ってきた類の機能なら Quick Spec で速く済みます。

### 4.2 Vibe モードとの違い

| | 成果物 | 承認ゲート |
|-|-------|----------|
| **Vibe モード** | **保存されない**（会話的で非構造的） | — |
| **Quick Spec** | **保存される**（標準の spec と同一形式） | **なし** |
| 標準の Feature Specs | 保存される | あり |

Quick Spec の成果物は標準の Feature Spec と**形式が同一**なので、そのまま任意の spec ワークフローで作業を続けたり、練り直したり、タスクを再生成したり、チャットで `#spec` として参照できます。

> **自動生成された要件に抜けがあったら**: `requirements.md` を直接編集するか、spec のチャットセッションで
> Kiro に追加・修正を依頼します。そのうえで **Sync Files** でタスクを再生成します。

## 5. Analyze Requirements（要件の矛盾を洗い出す）

**要件から設計に移る前に、論理的な矛盾・曖昧さ・抜けを分析させられます。** 個々の要件を単独で見るのではなく、**要件の集合全体を横断して推論**するため、読み合わせでは気づきにくい問題が見つかります。

### 5.1 何を見つけるか

| 種別 | 内容 |
|------|------|
| **論理的な矛盾** | 個別には成立するが、**まとめると成立不可能**な2つの要件 |
| **曖昧さ** | 「大きなファイル」「速い応答時間」のような、**実装が分かれる**言い回し |
| **制約の衝突** | 機能要件と非機能要件が**同時には満たせない** |
| **暗黙の前提** | 定義されていない概念や振る舞いへの参照 |
| **抜けているエッジケース** | ハッピーパスで扱われていない失敗モード・境界条件・同時アクセス |

### 5.2 呼び出し方と挙動

要件が生成されたあと、2箇所に **Analyze Requirements** が現れます。

- チャット内（他の進め方の選択肢と並んで）
- エディタの **Continue** ドロップダウン内（**Proceed to Design** と並んで）

> **分析には「秒」ではなく「分」かかります**（要件を横断する推論は通常の処理より計算負荷が高いため）。
> 結果が出るたびに、明確化の質問がチャットに流れてきます。

各質問には**関係する要件・問題の平易な説明・選べる修正案**が含まれます。独自の回答を入力することも、曖昧さが意図的なら質問を却下することもできます。質問を解消していくと、Kiro がエディタ上の `requirements.md` を更新します。

### 5.3 特に有効な場面

- 要件が多い複雑な機能
- ドメインが繊細なプロジェクト（**金融サービス・医療・コンプライアンス**）
- **Quick Spec のセッション**（要件が手作業のレビューなしで自動生成されたため）

小さい、あるいはよく理解している spec では分析を飛ばして設計に進んでかまいません。**要件を手で編集したあとに再実行**すると、影響を受けた要件とその相互作用が再分析されます。

## 6. タスクの実行

`tasks.md` には専用の実行インターフェースがあり、**状態がリアルタイムに更新**されます（進行中・完了）。タスクは個別にも一括でも実行できます。

### 6.1 並列実行（ウェーブ）

**Run all Tasks** を押すと、Kiro はタスク一覧を分析し、どのタスクが互いに依存しているかを判定して、**独立したタスクを同時に実行**します。ほとんどの Feature Spec では、**設定なしで実行時間が大幅に短縮**されます。

Kiro は `tasks.md` のタスクから**依存グラフ**を作り、独立したタスクを**ウェーブ**にまとめます。

| ウェーブ | 内容 |
|---------|------|
| **Wave 1** | 依存のないすべてのタスク。**同時に実行される** |
| **Wave 2** | Wave 1 で依存が満たされたすべてのタスク。同時に実行される |
| **Wave N** | すべてのタスクが完了するまで続く |

**ウェーブは順番に実行され、ウェーブ内のタスクは同時に実行されます。**

## 7. 始め方

| 順 | 操作 |
|----|------|
| 1 | Kiro ペインの **Specs** の下にある `+` ボタンを押す（またはチャットペインで **Spec** を選ぶ） |
| 2 | 機能開発かバグ修正かを聞かれる<br>・**Feature** を選んだ場合: 機能を説明し、**Requirements-First** か **Design-First** を選ぶ<br>・**Bug** を選んだ場合: バグを説明する |
| 3 | 各フェーズを進めて実装まで到達する |

## 9. Spec の正しさを検証する（プロパティベーステスト）

公式は「**spec correctness**」という考え方を示しています。答えたい問いは「**実装は本当に仕様どおりに動いているのか**」です。

### 9.1 例示ベースのテストとの違い

| 種別 | 書き方 | 限界 |
|------|-------|------|
| **例示ベース**（従来のユニットテスト） | 具体的な入力と1つの期待結果を手で書く | **カバー範囲が「思いついた例」に限られる**（人でも AI でも同じ） |
| **プロパティベース（PBT）** | 「常に成り立つべき一般的な規則」を述べる | ツールが**数百〜数千のランダム入力**を生成して規則を破ろうとする |

> 同じ考え方は *fuzzing*・*generative testing* とも呼ばれます。公式は「用語はおおむね交換可能」としています。

### 9.2 EARS 記法との相性

**プロパティ**は、扱うデータによらず常に真であるべき不変条件や契約を表す普遍的な言明です。

> 前提条件が成り立つ任意の入力集合について、期待される振る舞いが真である。

これは Kiro の **EARS 記法の要件とよく対応します**。公式の例:

> 「認証済みの任意のユーザーと、公開中の任意の出品について、そのユーザーはその出品を閲覧できる。」

具体例（車販売アプリ）:

| 種別 | テスト内容 |
|------|----------|
| 従来のテスト | ユーザーが Car #5 をお気に入りに追加 → Car #5 が一覧に現れる |
| **PBT** | **任意のユーザーと任意の車について**、WHEN ユーザーが車をお気に入りに追加する THEN システムは一覧に表示する SHALL |

### 9.3 shrinking（最小の反例に縮める）

PBT は反例を探して**赤チームのように**コードを壊そうとします。ランダムな入力で失敗が起きたとき、その入力はしばしば大きく雑然としています（200文字のユーザー名・1,000台の車のリスト）。

**shrinking はそれを、失敗を再現する最小の入力まで自動的に縮めます**（多くの場合は空文字1つや2要素のリスト）。根本原因が埋もれずに明らかになります。

違反が見つかると、Kiro は実装を自動更新するか、**仕様・実装・テストのどれを直すかの選択肢**を提示します。

> **形式検証ではありません**（公式明記）。ただし、手作業では書かないような広い範囲のシナリオについて、
> 実装が定義どおりに振る舞っているかの**証拠**を得られます。
