## 1. チャットを開く（3通り）

| 方法 | 操作 |
|------|------|
| **キーボードショートカット** | **`Cmd+L`**（Mac）/ **`Ctrl+L`**（Windows・Linux） |
| コマンドパレット | `Cmd+Shift+P` / `Ctrl+Shift+P` → `Kiro: Open Chat` |
| セカンダリサイドバー | 右上の Kiro チャットアイコンを **`Cmd+Opt+B`**（Mac）/ **`Ctrl+Alt+B`** で切り替える |

## 2. 日本語で使える

**Kiro のチャットは複数の自然言語での会話に対応しています。** 公式が挙げる対応言語:

Mandarin（中国語）・French・German・Italian・**Japanese（日本語）**・Spanish・Korean・Hindi・Portuguese（ほかにも利用できる言語があります）

**好きな言語で会話を始めると、Kiro が自動的に検出して同じ言語で応答します。** この能力は使用している大規模言語モデル（LLM）に由来します。

## 3. セッションの始め方（1.0 で二択ピッカーが廃止）

> ⚠️ **0.x からの変更点**: セッション開始時の **Vibe / Spec 二択ピッカーは 1.0 で廃止されました。**
> 公式は「This binary picker has been removed」と明記しています。
> 0.x での挙動は [02_update/03_migration-to-1.0.md](../02_update/03_migration-to-1.0.md#6-セッションの始め方が変わった対応不要) を参照してください。

**すべてのセッションはデフォルトエージェント（汎用のコーディングアシスタント）で始まります。**
新しいセッションを開くと「**Let's build**」画面が2つの入口を示します。

### 3.1 Free-flow chat（デフォルト）

**チャット入力欄に直接書くだけで、デフォルトエージェントと作業を始められます。** 事前の設定は不要です。

素早い探索・質問・説明にはこちらが向きます。

### 3.2 ワークフローから始める

**組み込みのワークフローエージェントを選ぶと、そのセッションのエージェントが切り替わります。**

| ワークフロー | 内容 |
|------------|------|
| **Spec** | 構造化された機能開発（要件 → 設計 → タスク、**各フェーズに承認ゲート**） |
| **Plan** | **読み取り専用**の計画モード。コードベースを調べ、変更を加えずに実装計画を作る |
| **Bug Fix** | 構造化されたバグ調査（原因究明 → 修正設計 → 実装） |
| **Quick Spec** | 高速版の Spec。**承認ゲートなし**で要件・設計・タスクを自動生成する |

> **Spec セッション専用のスラッシュコマンド（1.2.56）**: `/quick-spec`・`/architecture-selection`・`/bug-fix` は Spec セッションでだけスラッシュメニューに表示されます。
> それ以外のセッション（公式の表記では Vibe セッション）ではメニューに表示されず、入力しても指示は読み込まれません（公式 [Slash commands](https://kiro.dev/docs/ide/chat/slash-commands/)）。
> 公式によると、IDE 組み込みのスラッシュコマンドと CLI 組み込みのコマンドは別の一覧です。

**公式の目安**: **複雑な機能を作るとき・回帰のコストが高いバグを直すとき**は Spec を選び、
**素早い探索的な作業**は Free-flow chat のままにします。

Spec の詳細は [01_specs.md](01_specs.md) を参照してください。

#### Spec を選ぶ場面（公式）

| # | 理由 |
|---|------|
| 1 | **複雑な開発タスク** — 複雑な機能・アプリ全体・慎重な計画と実行が必要な大きなリファクタリング |
| 2 | **構造化された進め方** — 要件と実装の詳細を明確に文書化した、方法論的で段階的な開発が必要なとき |
| 3 | **チーム協業** — 複数のメンバーが実装計画を理解し、仕様に対する進捗を追う必要があるプロジェクト |
| 4 | **文書化の必要** — 将来の参照や知識共有のために、コードと並行して詳細な文書を生成したいとき |

### 3.3 セッション中の切り替え（いつでも可能）

**開始時に決める必要はありません。** 会話の途中でエージェントを切り替えられます。

| 操作 | 内容 |
|------|------|
| チャット入力欄の下部にあるエージェント名（例: **Default**）をクリック | **エージェントピッカー**が開く |
| チャット入力欄の **Build with spec** をクリック | 会話の途中から Spec ワークフローを呼び出す |
| 自作のエージェント | ピッカーの **WORKSPACE** / **GLOBAL** セクションに表示される |

素早い質問を Free-flow で始め、複雑になったら Plan エージェントに切り替え、実装では Default に戻す —
といった進め方ができます。組み込みエージェントの一覧は公式 [Built-in agents](https://kiro.dev/docs/custom-agents/built-in/) を参照してください。

## 4. 意図の自動判別（Smart intent detection）

**Kiro はメッセージを分析して、情報が欲しいのか動作が欲しいのかを判断します。**

| 入力の種類 | 例 | Kiro の反応 |
|----------|-----|-----------|
| **情報の要求** | "How does this work?"・"What's the purpose of this code?" | **コードを変更せず**、説明と文書で応答する |
| **動作の要求** | "Create a component"・"Fix this bug" | 必要なコード変更を提案または実装し、コマンドを実行し、ファイルを管理する |

**モードを切り替えるための明示的なコマンドは不要**です。自然な会話のまま両者を行き来できます。

## 5. コンテキストの渡し方

Kiro は**エディタで開いているファイル**（依存関係と構造を含む）を自動的に解析しますが、**`#` で明示的に追加**もできます。

チャット入力欄で `#` を打つと **14種のコンテキストプロバイダ**が使えます。

| よく使うもの | 内容 |
|------------|------|
| **`#codebase`** | プロジェクト全体から関連ファイルを Kiro が自動的に探す |
| **`#file`**（`#auth.ts` のように書く） | 特定のファイルを参照する |
| **`#terminal`** | ターミナルの最近の出力とコマンド履歴を含める |
| **`#spec`** | spec の全ファイルを参照する |

複数を組み合わせられます。

```
#codebase #auth.ts explain how authentication works with our database
```

**全14種の一覧と書き方の注意**は [04_reference/04_context-providers.md](../04_reference/04_context-providers.md) にまとめています。

## 6. コンテキストウィンドウと自動要約

> **公式ドキュメント上の位置づけ**: 自動要約は 2026-08 の公式サイト再構成で `/docs/chat/summarization/` から `/docs/compaction/` へ移転・改称し、**IDE 固有機能から Compaction という共通機能**として位置づけ直されています。CLI 版・Web 版も同じ仕組みです。

すべての言語モデルには「**コンテキストウィンドウ**」（一度に扱えるテキストの最大量）があります。長さはモデルによって異なります（[04_reference/05_models.md](../04_reference/05_models.md)）。

Kiro は会話中の**過去のメッセージすべて**をコンテキストとしてモデルに送ります。そのため会話が長くなると上限に近づきます。

| 項目 | 内容 |
|------|------|
| **自動要約の閾値** | 使用量が**モデルの上限の 80%** に達したとき |
| 挙動 | **会話中の全メッセージを自動的に要約**して、コンテキスト長を上限より下に戻す |
| 確認方法 | チャットパネルの**コンテキスト使用量メーター**で、上限の何%を使っているか分かる |

> **1.1 での改善**: 要約した会話は、システム指示と要約から組み立て直されるようになり、その後のターンが適切なコンテキストを保つようになりました（[1.1.14](../02_update/01_changelog.md#v1-1-14)）。

> **長い作業では要約が起きることを前提に**してください。重要な決定事項は spec やステアリングファイルに
> 書き出しておくと、要約で失われません。

> **モデルのフォールバック通知（1.3.0 で追加）**: モデルが依頼を断る、または利用できないとき、継続するモデルをトランスクリプトに表示し、
> 変更が1ターンだけか会話の残り全体かも示します（[1.3.0](../02_update/01_changelog.md#v1-3-0)）。
> 公式 [Models](https://kiro.dev/docs/models/#model-fallback-notices) は、この動作を**ローカルの V3 セッション**の説明として書いています。
> IDE ではサブエージェント内で起きたフォールバックがそのサブエージェントのアクティビティ内に表示され、同じモデルでの再試行は一時的な再試行通知として表示されます。
> モデルの一覧は [04_reference/05_models.md](../04_reference/05_models.md) を参照してください。

## 7. サブエージェント（並列実行と委譲）

> **公式ドキュメント上の位置づけ**: サブエージェントは 2026-08 の公式サイト再構成で `/docs/chat/subagents/` から `/docs/custom-agents/subagents/` へ移転し、**IDE 固有機能から Custom agents 配下の共通機能**として位置づけ直されています。CLI 版も同じ仕様です。

**サブエージェントは、複数のタスクを並列に実行したり、特定のタスクを専門のサブエージェントに委譲する仕組みです。** Kiro が適切に自動起動しますが、「Run subagents to...」のようなプロンプトで手動起動もできます。

> ⚠️ **Workflows を有効にすると委譲の経路が変わります**（1.2.4 以降）。公式 [Workflows](https://kiro.dev/docs/workflows/) ページによると、
> Workflows が無効なメインセッションでは、メインエージェントは `invoke_sub_agent` で委譲します。
> **CLI V3 以外のクライアントで Workflows を有効にすると、メインセッションの委譲は Workflows（`run_workflow`）経由になり**、
> 1つのカスタムエージェントをバックグラウンドで動かすときは `run_workflow(agent://<name>)` を使います。
> Workflow の中で動くエージェントは、その設定が許す範囲で引き続きサブエージェントを使えます。詳細は [§13](#13-workflows124-で追加) を参照してください。

### 7.1 組み込みのサブエージェント（2種）

| 種別 | 用途 |
|------|------|
| **context gathering** | プロジェクトを探索し、関連するコンテキストを集める |
| **general purpose** | それ以外のすべてのタスクを並列化する |

### 7.2 動作の仕組み

| 項目 | 内容 |
|------|------|
| 実行 | サブエージェントは**並列に動く** |
| メインエージェント | **すべてのサブエージェントの完了を待ってから**先に進む |
| **コンテキスト** | **各サブエージェントが独自のコンテキストウィンドウを持つ**（メインのコンテキストが汚れない） |
| 結果 | 完了時に**自動的にメインエージェントへ返される** |

**これが速度以外の価値でもあります**（公式の例: 複数のチケットを並列に取得・分析する場合、逐次より速いだけでなく、ツール呼び出しとチケットの詳細が各サブエージェント内に留まりメインのコンテキストを汚さない）。

<a id="subagent-capabilities"></a>

### 7.3 サブエージェントで使えるもの・使えないもの（重要）

| 機能 | サブエージェント内 |
|------|-----------------|
| **ステアリングファイル** | ✅ メインエージェントと**まったく同じように動く** |
| **MCP サーバ** | ✅ メインエージェントと**まったく同じように動く** |
| **Specs** | ❌ **アクセスできない** |
| **Hooks** | ❌ **発火しない** |

### 7.4 カスタムサブエージェント

`~/.kiro/agents`（グローバル）または `<workspace>/.kiro/agents`（ワークスペース）に Markdown ファイルを作ります。本文にプロンプトを書き、YAML front matter で属性を定義します。

```markdown
---
name: code-reviewer
description: Expert code review assistant.
tools: ["read", "@context7"]
model: claude-sonnet-4
---

You are a senior code reviewer.

## Your Responsibilities
- Review code for correctness, performance, and security
...
```

**属性（`name` のみ必須）**:

| 属性 | 内容 | 例 | 省略時の既定 |
|------|------|-----|-----------|
| **`name`** | エージェントの名前 | `code-reviewer` | **`.md` ファイル名** |
| `description` | エージェントの説明 | `Expert code review assistant` | 説明なし |
| `tools` | アクセスできるツールの配列 | `["@builtin", "@context7"]` | **ツールなし** |
| `model` | 使用するモデル | `claude-sonnet-4` | **チャットで現在選択中の LLM** |
| `includeMcpJson` | true ならすべての MCP ツールを含める | `true` | `false` |
| `includePowers` | true なら **Powers** 内のすべての MCP ツールを含める（Powers = MCP サーバ・ステアリング・フックのバンドルを動的に読み込む仕組み。[0.7 の導入時の説明](../02_update/02_changelog-0x.md#powers)・公式 [`/docs/powers`](https://kiro.dev/docs/powers/)） | `true` | `false` |

**`tools` フィールドで使える指定**:

| 指定 | 内容 |
|------|------|
| `read` | 組み込みのファイル読み取りツールすべて |
| `write` | 組み込みのファイル書き込みツールすべて |
| `shell` | 組み込みのシェルコマンド関連ツールすべて |
| `web` | 組み込みの Web ツールすべて |
| `spec` | 組み込みの spec 関連ツールすべて（**Spec モードでのみ有効**） |
| `@builtin` | 組み込みツールすべて |
| `@<mcp_server>` | 特定の MCP サーバのツールすべて（例: `@figma`） |
| `@<mcp_server>/<tool>` | 特定の MCP サーバの特定のツール（例: `@figma/get_figjam`） |

**ワイルドカードに対応**します（`tools: ["*"]` で組み込みと MCP のすべて、`tools: ["@figma/*"]` で figma サーバのすべて）。

### 7.5 呼び出し方

Kiro はサブエージェントを起動するとき、**`description` フィールドをもとに適切なカスタムエージェント設定を自動選択**します。明示的に指定することもできます。

| 方法 | 例 |
|------|-----|
| 自然言語で指定 | "Use the code-reviewer subagent to find performance issues in my code" |
| **スラッシュコマンド** | `/code-reviewer find performance issues in my code` |

**サブエージェントはスラッシュコマンドとしても現れます。**

カスタムエージェントの詳細は [07_custom-agents.md](07_custom-agents.md) を参照してください。

## 8. チェックポイント（変更を巻き戻す）

> **公式ドキュメント上の位置づけ**: チェックポイントは 2026-08 の公式サイト再構成で `/docs/chat/checkpoints/` から `/docs/checkpoints/` へ移転し、**IDE 固有機能から共通機能**として位置づけ直されています。CLI 版の `/rewind` コマンドも同じ仕組みです。

**プロンプトを送るたびに Kiro は「チェックポイント」を作ります。** チャット履歴に目印として現れ、**Restore** を押すと**コードベースと Kiro のコンテキストの両方**をその時点まで巻き戻せます。

| 巻き戻す対象 | 内容 |
|------------|------|
| コードベース | そのチェックポイント以降に Kiro が加えた変更が戻る |
| コンテキスト | そのチェックポイント以降のチャットのやり取りが破棄される |

**安全網として機能します** — 複数のアプローチを試す・タスクごとに違うモデルを試す・エージェントの誤解から復帰する、といったことに使えます。

### 8.1 仕組みと限界（重要）

チェックポイントは、Kiro のエージェントが**組み込みのファイル変更ツール**でファイルを変更するたびに、その内容をスナップショットして実現されています。

> **Kiro のエージェント以外による変更は追跡されません。**

| 追跡されない例 | 結果 |
|--------------|------|
| **自分で手動編集した** | 巻き戻すと、その変更は失われる |
| **コードフォーマッタを走らせた** | 同様に失われる |
| **MCP ツールによるファイル変更** | 追跡されない |
| **エージェントが実行した bash コマンドによる変更** | 追跡されない |

**エージェントが実行したコマンドの結果は巻き戻せない**点に注意してください。

### 8.2 Revert（直前のターンだけ戻す）との違い

エージェントがファイルを変更してターンを終えると、チャット入力欄のすぐ上に **Revert** の選択肢が出ます。

| | **Revert** | **Checkpoint** |
|-|-----------|---------------|
| 範囲 | **最新のターンのみ** | **複数のターンにまたがれる** |
| 対象 | **ファイルの変更のみ** | ファイルの変更**＋コンテキストの破棄** |

## 10. 会話の書き出し

### 10.1 Markdown で書き出す

書き出したい会話のタブを**右クリック → Export Conversation**。Markdown（`.md`）形式で出力されます。

### 10.2 zip で書き出す（Export Chat）

**プロンプト・応答・ツール呼び出し・コードブロックを含むスレッド全体**を、可搬な zip ファイルとして保存できます。

| 順 | 操作 |
|----|------|
| 1 | 書き出したいチャットタブを右クリックする |
| 2 | **Export Chat** を選ぶ |
| 3 | zip の保存先を選ぶ |
| 4 | zip を展開して中身を見る |

**zip の中身**（セッション ID の名前のディレクトリ）:

| ファイル | 内容 |
|---------|------|
| **`session.json`** | セッションのメタデータ（エージェント名・モデル・タイムスタンプなど） |
| **`messages.jsonl`** | 会話全体（改行区切り JSON・1行1メッセージ。プロンプト・応答・コードブロック・ツール呼び出し） |
| `sub-executions/*.jsonl` | セッション中に走ったサブエージェントの実行のメッセージ（**サブエージェントを使った場合のみ**） |

> **書き出しは読み取り専用です。** 書き出したセッションを Kiro に**読み込み直すことはできません**。

**公式が挙げる用途**: チームでの共有（複雑な問題を解いたセッションのアプローチを共有）／文書化（アーキテクチャの決定を説明したセッションを保存）／デバッグ（想定外のエージェントの挙動を調査する）／アーカイブ（履歴を消す前に重要なセッションを保存）。

## 11. Dockable chat（チャットをエディタタブで開く）

**任意のチャットセッションを、ソースファイルと同じ幅のエディタタブとして開けます。** 分割・ドッキング・自由な配置ができます。

| 順 | 操作 |
|----|------|
| 1 | セッションタブバーでチャットタブを右クリックする |
| 2 | **Open in Editor** を選ぶ |

通常のエディタタブとして、次のことができます。

- ドラッグして並べ替える・別のエディタグループへ移す
- ソースファイルと**横または縦に分割**して並べる
- **複数のチャットタブを同時に開く**

### 11.1 チャットパネルとの関係

| 項目 | 内容 |
|------|------|
| 表示内容 | **エディタタブとサイドパネルは同じセッションを表示する** |
| メッセージ送信 | **どちらから送ってもエージェントに届く** |
| エディタタブを閉じた場合 | **セッションはパネル側で継続する。何も失われない** |
| セッション管理（作成・一覧・切り替え） | **チャットパネルが本拠** |

**公式が挙げる使いどころ**: 長いコード生成を全幅で確認する／分割エディタでチャットとソースを並べて参照する／マルチモニタでチャットを別のエディタグループに置く／サイドパネルが今の会話に対して狭く感じるとき。

### 11.2 Agent Focus Mode への切り替え

IDE 右上の **Agent Focus** ボタンでセッションを Agent Focus Mode に移せます。**チャット中心の全画面レイアウトで、複数の並列セッション**を扱えます。もう一度押すと Editor View に戻ります。

詳細は [09_agent-focus-mode.md](09_agent-focus-mode.md) を参照してください。

### 11.3 エディタタブのライブ状態表示（1.3.0 で追加）

IDE 1.3 以降、エディタタブに開いたチャットまたは Workflow ステップの状態が、タブの点で分かります（公式 [Dockable chat](https://kiro.dev/docs/ide/chat/chat-in-editor/#live-session-status)・[1.3.0](../02_update/01_changelog.md#v1-3-0)）。

| タブの表示 | 意味 |
|----------|------|
| **緑の点** | チャットまたは Workflow ステップが作業中 |
| **警告の点** | セッションがあなたの入力を待っている（権限の判断を含む） |
| アイドルに戻ったとき | チャットはアイコンなしに、Workflow ステップは Workflow アイコンに戻る |

タブのタイトルは変わりません。IDE の設定でエディタのアイコンを非表示にしている場合は、この点も表示されません。

## 12. Agent Artifacts（1.1 で追加）

**エージェントがチャットセッション中に作る、後から開き直せる成果物です。** ドキュメント・図・プレビューを会話の中に埋もれさせず、セッションが利用できる間は Artifact として開き直せます。

| 項目 | 内容（公式） |
|------|------------|
| **位置づけ** | **セッションの出力であり、プロジェクトのファイルではない**。Artifact を作ってもリポジトリには追加されず、バージョン管理にもコミットされない。プロジェクトに残したい内容は、別途 Kiro にプロジェクトのファイルとして作成・更新させる |
| **対応する種類** | Markdown ドキュメント・Mermaid 図・コード・SVG・HTML・画像・PDF ドキュメント・Microsoft Office ドキュメント |
| **表示の制約** | PowerPoint（`.pptx`）はテキストのアウトラインとして表示される。**HTML の Artifact はスクリプトを実行しない**ため、JavaScript に依存する操作は使えない |
| **サイズ上限** | Artifact 1件あたりのペイロードは **最大 12 MB** |
| **確認のしかた** | エージェントが Artifact を作ると、チャットのトランスクリプトにコンパクトなプレビューが表示される。プレビューを開けば会話を探さずに中身を確認できる |
| **Agent Focus Mode では** | プレビューを選ぶと、セッション詳細パネルがその Artifact を開いて表示する。パネルにはセッションのすべての Artifact が並び、後から戻れる。**Open in IDE** でエディタで開く（[09_agent-focus-mode.md](09_agent-focus-mode.md#12-セッション詳細パネルartifacts-と-workflows)） |
| **保存先** | Kiro のグローバルなアプリケーションストレージに**セッションごと**に保存される。プロジェクトの `.kiro` ディレクトリの外にあり、ローカルの Steering・Specs・Hooks などのプロジェクト構成を上書きしない |

> **Artifact はソース管理の代わりではありません。** 公式は、ふだんのレビュー・バックアップ・バージョン管理の流れに
> 乗せる必要がある重要な内容は、プロジェクトなどの永続的な場所に保存するよう案内しています。

## 13. Workflows（1.2.4 で追加）

**再利用できる複数ステップのエージェントの計画を、バックグラウンドで実行する仕組みです。** 要件・設計・実装・独立したレビュー・検証が必要な機能開発のように1つのセッションに収まらない作業や、見守るより任せたい調査を、計画を持ったエージェントのチームに渡します。**メインの会話で作業を続けている間に、委譲した作業が進みます。**

> ⚠️ **名前の似た別物が2つあります**（公式が明記）。Agent Focus Mode などでセッション開始時に選ぶ**組み込みのワークフロー**（Spec・Plan・Bug Fix・Quick Spec。[§3.2](#32-ワークフローから始める)）と、Kiro Crew の Workflows は、ここで扱う Workflows とは別のものです。

Workflows は IDE・CLI・Web で共通の機能です（レシピは3つのクライアントで同じファイル）。有効化の方法・レシピの入手元・操作できる内容はクライアントごとに異なるため、以下は **IDE での使い方**を中心にまとめます。

### 13.1 有効にする（既定で無効）

| 順 | 操作 |
|----|------|
| 1 | プロジェクトの **Workspace Configuration** を開く（1.2.4 の changelog は Agent Focus の Workspace Configuration と説明） |
| 2 | **Workflows** を選ぶ |
| 3 | Workflows を有効にする |
| 4 | **新しいチャットセッションを開始する** |

背後の設定は **`kiroAgent.workflows.enabled`** です（Settings から設定しても同じ）。**Workflows が表示されない場合、そのアカウントではまだ利用できません**（公式）。

### 13.2 始め方

**先にレシピを書く必要はありません。** 親チャットで目的と、どの程度の構造やレビューが欲しいかを伝えると、Kiro がその作業向けのワークフローを提案し、ステップと担当エージェントを決めて起動します。

| 項目 | 内容（公式） |
|------|------------|
| ステップごとの指定 | カスタムエージェント・使うモデル・思考の深さ（effort）をステップごとに指定できる。分担のしかたはプロンプトやステアリングファイルでも誘導できる |
| 同梱のレシピ | `investigate`（読み取り専用の調査）・`feature-pipeline`（段階的な機能開発）・`publish-pr`（プルリクエストを開き、レビューの指摘に対応する）。名前を挙げて入力を渡せば使える |
| 形式 | Kiro は **JSON** でレシピを生成する。**YAML** にも対応 |
| **コスト** | 複数のエージェントを調整しレビューを繰り返すため、**1つのセッションより多くのトークンを使う**。小さな作業はチャットで済ませるよう公式は案内している |
| **保存済みレシピをスラッシュコマンドで起動**（1.3.0 で追加） | チャット入力欄で `/workflow-run` を入力またはスラッシュメニューから選び、絞り込まれた一覧からレシピを選んで、インラインフォームの入力を埋めて **OK** を押し、コマンドを送信する。Kiro はレシピと入力を検証し、**モデルのターンなしで**実行を開始して、新しい実行を開いた **Workflows** を表示する。送信前にコマンドのチップを選ぶと入力を変更できる。`key="value"` の形で入力を直接書くこともできる（例: `/workflow-run investigate brief="Trace timeout settings" report_path=".kiro/reports/timeouts.md"`）。Workflows が利用できない、またはそのセッションでオフのときは、実行を開始しない |

> **`/workflow-run` の表示（1.3.11）**: コマンドとレシピは1つのチップとして表示され、すべての入力が `key=value` で並びます。矢印キーでの移動は最後のレシピで止まり（先頭に戻りません）、入力欄は型のラベルを表示せず、1つのメッセージで Kiro が受け付けるワークフローコマンドは1つです。
>
> **提案されたステップの承認**: Kiro がプロンプトからワークフローを作るときは、ステップの実行前に権限カードで確認します。詳細は [§13.7](#137-提案されたステップの承認145-で追加) を参照してください。

> 公式は、同梱のレシピは「実行できる例」であり、必須の手法でも、すべてのクライアントの版で必ず入っている一覧でもないと説明しています。**実行する前にレシピを確認してください。** 副作用はレシピのプロンプトと、選ばれたエージェントのツール・権限の両方で決まります。

### 13.3 しくみ（5つの考え方）

| 考え方 | 意味（公式） |
|-------|------------|
| **Step** | 1つのエージェントが、焦点を絞ったコンテキストを持つ**専用のセッション**で動く。ステップは他のステップのセッションを読めず、前の結果は明示的な引き継ぎでだけ受け取る |
| **Handoff** | 取り込んだ出力や宣言された Artifact が、後のステップに根拠を渡す |
| **Branch and join** | 独立したエージェントが同じ作業を評価し、方針に従って結果をまとめる |
| **Loop** | 根拠が条件に一致するか、安全上の上限に達するまで、ステップの組を繰り返す |
| **Wait** | 外部のシステム（プルリクエストや、自作スクリプトで確認できるもの）を見張る。変化がない間はモデルのターンを消費しない |

各ステップは**新しいコンテキストを持つ専用のセッション**で動くため、たとえばレビュー担当はコーディング担当の推論を引き継がずに作業を評価できます。ワークフローはステップの区切りで残りの作業を見直せますが、完了した作業はそのまま残り、実行中のステップが途中で書き換えられることはありません。Kiro はノードの区切りで実行のチェックポイントを取るため、一時停止や再接続の後に完了した作業を最初からやり直す必要はありません。

### 13.4 IDE での確認と操作

| 項目 | 内容（公式） |
|------|------------|
| 起動 | 親チャットで Kiro に頼む。1.3.0 以降は `/workflow-run` で保存済みレシピを選ぶこともできる（[§13.2](#132-始め方)） |
| 実行の一覧 | 親チャットの上にある **Workflows** に、そのセッションの実行が並ぶ。実行を展開するとステップのツリーと状態が見える |
| ステップを開く | ステップを選ぶと専用の **Workflow step** タブが開く。ステップ・エージェント・モデル・effort・アクティビティと、**Message this step's agent** 欄を持ち、実行中も親チャットの横に置いておける |
| 親チャットへのステップ通知（1.3.11） | ステップからのメッセージは、親チャットで**まず1行の状態行**（**Info**・**Completed**・**Needs input**・**Failed**）として表示される。行を展開すると全文が読める。行には、ステップ名・（異なる場合は）エージェント名・実行名・時刻も表示される。行から操作できる場合がある（**Info**／**Completed** は、Kiro がソースのセッションを把握しているときに **Open step session**。**Needs input** は **Answer** に続けてステップ名、**Failed** は **Open** に続けてステップ名で、どちらも実行中のステップセッションがある行のみ）。完了や停止といった実行の結果の行は1行のままで、展開できない |
| 入力待ち | 入力が必要な実行は **Needs you** 状態になる。止まっているステップを選んで直接答えるか、通知行の **Answer** を選ぶか、親チャットのメインエージェントに答えを渡してもらう |
| **操作** | **Pause**（次のノードの区切りで協調的に一時停止）・**Resume**（一時停止した実行を再開）・**Stop**（実行中の作業を中断し、実行を `aborted` にする） |
| Retry | **現在の IDE の UI には Retry がない**。完了・失敗した後にもう一度実行するときは、ワークスペースを確認したうえで新しい実行として始める |
| 空の **Workflows**／**Artifacts** ビュー（1.3.0） | 空のビューに、そこに何が入るかと最初の項目の追加のしかたを表示する |
| 実行一覧の表示（1.3.0） | 実行中の Workflow は終了した実行より上に並び、実行が一時停止または入力待ちになっても行が飛び回らない。年齢ラベルは一覧を開いている間も更新され、展開できる行にはシェブロンが付く。実行中の Workflow が1つだけなら展開された状態で開く |
| 接続エラー時の再試行 | 接続の失敗では、同じステップのセッションで**最大24時間**再試行し、最後の試行も失敗したら実行を一時停止する。最初の5分は約1分に1回、以降は約2分の待ち時間（ばらつきあり）。成功したターンまたは明示的な再開で、新しい再試行期間が始まる。サービスの 5xx エラー・スロットリング・停止したストリームには、より短い別の再試行動作が適用される（公式 Run and manage workflows） |
| フィードバック用アンケート（1.2.56） | チャットの Workflows ドロワーからデスクトップアプリで短いアンケートを開ける。GovCloud・AWS 分離リージョン・中国リージョンでは利用できない（1.2.56 の changelog） |

> ⚠️ **Stop はファイルの変更を元に戻しません**（公式）。中断した実行が残した編集は、自分で確認するか元に戻してください。
> また、**Workflows は Git のブランチを分けたり worktree を作ったりしません**（公式の Operational limits）。
>
> 公式の Workflows ページには、これと並んで次の記述があります。IDE では、Kiro はリポジトリのファイルを変更するワークフローに、**実行開始時にチェックアウトされているブランチ**を使うよう指示します。ワークフローが worktree を使う場合は、そのブランチから worktree を作り、最後に同じブランチへリベースするよう指示します（1.2.56 の修正に対応）。
> Operational limits の上記の記述も、現行の Run and manage workflows ページ（2026-10-20）に残っています。

> **再試行と親チャットへの更新の説明**: 1.2.37 の changelog は、ステップが最大24時間再試行し、**5分後に親チャットへ更新を出す**と説明しています。公式の Run and manage workflows ページ（2026-10-20）は、最大24時間・最初の5分と以降の間隔・再試行期間の開始条件を説明していますが、親チャットへの更新については記述がありません。このため、親チャットへの更新の詳細（表示内容など）は未確認です（公式の記述に載っていません）。

**実行の状態**（公式。クライアントによらず共通）:

| 状態 | 意味 |
|------|------|
| `running` | ノードを実行中またはスケジュール中 |
| `paused` | ステップが入力を待っている・要求した一時停止がノードの区切りで効いた・繰り返しが上限（`maxIterations`）に達した、の3通り |
| `completed` | 必須のトップレベルのノードがすべて完了した |
| `failed` | ノードが失敗し、それが実行全体に伝わった |
| `aborted` | 実行が停止された、または繰り返しが `onMaxIterations: "abort"` を使った |

### 13.5 レシピの置き場所

| 置き場所 | 内容 |
|---------|------|
| **プロジェクト** | `.kiro/workflows/` に `*.workflow.json`・`*.workflow.yaml`・`*.workflow.yml` のいずれかで置く。同じ名前（stem）で複数の拡張子がある場合は **JSON が優先**され、もう一方は競合として報告される |
| **ユーザー** | `~/.kiro/workflows/`（ワークスペースをまたいで使う個人のレシピ） |
| アカウントに同期されたレシピ・同梱のレシピ | アカウントとクライアントの版によって異なる |

**同じ名前のレシピの優先順位**は、プロジェクト → ユーザー → 同期されたアカウントのレシピ → 同梱のレシピの順です。上位のレシピが無効でも、下位の有効なレシピは隠されません。

> ⚠️ **信頼していないワークスペースのレシピは読み込まれません**（1.2.4）。ホームやクラウドのレシピディレクトリからリンクで辿れるものも含めて、
> ワークスペースのレシピはそのワークスペースを信頼するまで読み込まれません（自分のホーム・クラウド・同梱・生成されたレシピは使えます）。
> また、`.kiro/workflows/` と `~/.kiro/workflows/` へのエージェントの書き込みは**常に確認**が求められます
> （[04_reference/03_permissions.md](../04_reference/03_permissions.md#71-kiro-スコープの不変条件上書き不可)）。

**制限**（公式の Operational limits）: 入れ子は最大8階層、静的な `step` ノードは最大50個。すべての `repeat` は正の `maxIterations` を持ち、条件は各反復の後に評価されるため最低1回は実行されます。`parallel` は各ブランチに独自のコンテキストと結合方針（`all`・`allSettled`・`any`）を与えますが、公式は「速度ではなく分離と結合のために使う」よう案内しています。

> レシピの書き方（ルートのフィールド・ノードの種類・テンプレート変数・停止条件・モデルと effort の指定・起動前の検証）は
> 公式 [Author workflows](https://kiro.dev/docs/workflows/authoring/) に全量が掲載されています。本サイトでは扱いません。

### 13.6 うまくいかないとき（IDE に関係するもの）

| 症状 | 確認すること（公式） |
|------|------------------|
| IDE に Workflows の表示がない | ワークスペースで Workflows を有効にしてから、**新しいチャットセッションを開始する** |
| レシピが現れない | レシピの置き場所と優先順位を確認する。プロジェクトのファイルは `.kiro/workflows/` に、対応する拡張子で置く |
| 中断した実行が編集を残した | 中断はファイルの変更を元に戻さない。ワークスペースを確認するか元に戻す |
| 止まっているステップが返信を無視する | 添付ファイルや親チャットだけでなく、**そのステップ自身のセッション**にテキストを送る |

### 13.7 提案されたステップの承認（1.4.5 で追加）

**Workflows を有効にしていると、IDE は提案されたステップを実行する前に権限カードで確認します。**（公式 [Run and manage workflows](https://kiro.dev/docs/workflows/manage/#review-proposed-steps-in-kiro-ide)・[1.4.5](../02_update/01_changelog.md#v1-4-5)・[1.4.10](../02_update/01_changelog.md#v1-4-10)）

| 項目 | 内容（公式） |
|------|------------|
| カードが出る場面 | ①Kiro がプロンプトからワークフローを作るとき ②エージェントが実行にステップを追加するとき ③エージェントが残りの計画を置き換えるとき |
| カードの内容 | 提案されたステップとその説明をプレビューする。非常に大きな計画では表示される詳細が少なくなることがある。提案が現在の計画のステップを残す場合は、**Runs after** の下にそれらを一覧する |
| 選択肢 | **Allow**（提案されたステップを実行する）・**Deny**（却下する）。カードに **Always allow**／**Always deny** も出る場合、その選択は以降のワークフロー計画の要求に対する判断として保存され、Kiro はカードを表示せずに適用する（公式 [Interactive approval flow](https://kiro.dev/docs/permissions/#interactive-approval-flow)） |
| 変更を依頼する | チャット入力欄にフィードバックを入力して **Enter** を押す。カードが開いている間、送信ボタンのツールチップは **Send feedback on the workflow plan (Enter)** になり、メッセージは新しいターンの開始ではなく**計画へのフィードバック**としてエージェントに渡る。エージェントはフィードバックから計画を修正し、承認後のステップは**元の依頼ではなく修正後の計画**に従う（1.4.10） |
| 添付ファイル | 計画へのフィードバックでは**非対応**。メッセージを送るには添付を外す。下書きは保持される |

## 14. ターミナルコマンドのタイムアウト（1.1.70 で追加）

エージェントが実行する**ローカルの**ターミナルコマンドの既定のタイムアウトを、Settings の **`kiroAgent.terminalCommandTimeout`** で変えられます。

| 項目 | 内容（公式 Terminal integration ページ） |
|------|------------------------------------|
| 単位と形式 | **ミリ秒の整数** |
| 無効な値 | `1000` 未満・小数・数値以外は**未設定**として扱われる |
| 上限 | `1800000` を超える値は `1800000`（30分）に切り詰められる |
| 既定値 | 空の場合は組み込みの既定値 **`120000`（2分）** |
| 反映 | 開いているローカルセッションでも、**再起動なしで次のコマンドから**反映される |
| 優先順位 | **コマンド個別のタイムアウトがこの既定値より優先**される |
| クラウドセッション | 組み込みの既定値を使う（この設定は効かない） |

## 16. Memory（1.4.0 で追加）

**Kiro がチャットセッションをまたいで、有用なコンテキストを引き継ぐ仕組みです。** リポジトリのコマンドや規約・訂正された内容・デバッグで分かったこと・すでに除外した方法・あなたの作業の好みなどを覚え、あとで関係するときに使います（公式 [Memory](https://kiro.dev/docs/memory/)・[1.4.0](../02_update/01_changelog.md#v1-4-0)・[1.4.10](../02_update/01_changelog.md#v1-4-10)）。

| 項目 | 内容（公式） |
|------|------------|
| 記録の形 | 1件のメモリは、タイトル・説明・内容を持つ記録。過去の会話のコピーではない |
| 保存先 | **ユーザーアカウント単位**でローカルに保存される（ワークスペース単位ではない）。同じマシンの Kiro IDE と Kiro CLI は保存済みのメモリを共有するが、**Memory の設定はアプリごとに別** |
| Steering との違い | Memory は作業から Kiro が学び、あとで思い出すコンテキスト。常に守らせたいルールは Steering に書く（公式の案内） |

### 16.1 設定と学習・参照のレベル

IDE では**1つのユーザー設定**で Memory を制御します。**既定は Off** です（1.4.10 で既定が Off になりました。すでにレベルを選んでいる場合は、更新後もその選択が保たれます）。

| 順 | 操作 |
|----|------|
| 1 | アクティビティバーの **Memories** アイコンを選び、Memory ビューを開く |
| 2 | Memory settings の歯車を選ぶ（Settings が **Kiro Agent: Memory** の設定で開く） |
| 3 | アクセスレベルを選ぶ |

| アクセスレベル | 内容（公式） |
|--------------|------------|
| **Use and learn** | メモリを使い、権限の範囲で変更もできる。メモリの作成と改善も自動で行う |
| **Use but don't learn** | メモリを使い、あなたが頼んだときに権限の範囲で変更できる。メモリを自動では作成・更新しない |
| **Use only** | 既存のメモリを使うだけで、頼まれても作成・更新・削除をしない（読み取り専用） |
| **Off** | メモリを使わず、変更もしない（既定） |

- Memory のオンとオフの切り替え、および **Use only** への出入りは、**新しいセッションから**適用されます。IDE は「Memory settings updated. The change applies to new sessions.」と **Start new session** の操作を表示します。**Use and learn** と **Use but don't learn** の間の切り替えは、開いているローカルセッションで即時に有効になります。
- Memory は**ユーザー設定**です。ワークスペース設定に書いた値は効果がありません。
- **信頼していないワークスペース**では、**Use and learn** または **Use but don't learn** でも、チャットからメモリを追加・変更・削除できません（読み取りはできます。[Workspace trust](https://kiro.dev/docs/permissions/#workspace-trust)）。
- **設定キー名（`settings.json` に書く名前）は未確認です**（公式は設定の表示名 **Kiro Agent: Memory** だけを記載しており、キー名の記述はありません）。

### 16.2 Memory ビューで確認・削除する

アクティビティバーの **Memories** アイコンで Memory ビューを開くと、**Global** のメモリと、現在のウィンドウで開いているリポジトリに紐づくメモリが一覧されます。

| 項目 | 内容（公式） |
|------|------------|
| type | メモリが持つ情報の種類。多くは **Preference** か **Fact**。IDE が名前を付けられない種類は **Other** と表示される |
| location | メモリが適用される場所。**Global** またはリポジトリ名 |
| 行の内容 | タイトル・作成からの経過時間・1行の要約・type・location |
| 検索と絞り込み | **Search memories...** にタイトルまたは要約を入力して絞り込む。**All memories** から TYPE または LOCATION で絞り込める。フッターに保存されているメモリの件数を表示する（絞り込み中は「3 of 12 memories」のように表示） |
| 開く | 行を選ぶと、メモリがエディタタブで開く。type・location・作成時刻・**Summary**・**Content** と、**Refresh**・**Delete** のボタンが表示される |
| 削除 | 行を右クリックして **Delete** を選ぶか、タブの **Delete** を選ぶ。削除の前に確認が表示される |
| 再読み込み | ビューのタイトルバーの **Refresh Memories** |

**Use only** のときでも、Memory ビューからメモリを削除できます。メモリの内容を直したいときはチャットで Kiro に頼みます。Kiro が変更できるのは、**Use and learn** または **Use but don't learn** で、信頼したワークスペースの場合だけです。

### 16.3 セッション中の表示

Kiro がメモリを使うと、チャットはその動作を折りたためる項目にまとめて表示します。

| 表示 | 内容（公式） |
|------|------------|
| **Memory accessed (N)**・**Memory created (N)**・**Memory updated (N)** | 関係したメモリのタイトルを一覧する。タイトルにカーソルを合わせると type と要約が見え、accessed・created・updated・一覧の項目ではタイトルを選ぶとメモリが開く |
| **Memory deleted**・**Memory imported** | deleted は存在しなくなったメモリの名前、imported は取り込み元の名前を示す。タイトルは開かない |
| **Couldn't save memory**・**Memory not saved** | 失敗した、または Kiro が確認できなかったメモリの呼び出しは、別のカードとして表示され、エージェントの結果テキストが付く。取得できる場合はメモリ名も表示される |
| コンテキスト使用量 | メモリがコンテキストを使うと、チャット入力欄のコンテキスト使用量の表示から開く **Context Usage** の **Steering files** の次に **Memory** の行が現れる |

> 1.4.10 では、メモリを一覧するよう頼んだとき、セッションに読み込まれていないメモリだけが一覧される問題が修正されました（[1.4.10](../02_update/01_changelog.md#v1-4-10)）。
