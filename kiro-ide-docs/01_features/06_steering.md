# Steering（エージェントへの持続的な指示）

**チャットのたびに規約を説明せずに済むよう、Markdown ファイルで恒久的な文脈を渡す仕組みです。**

- **一次情報**: [Steering](https://kiro.dev/docs/steering/)（公式ページ更新日: 2026-08-12）
- **ファイルの置き場所**: [04_reference/01_kiro-directory.md](../04_reference/01_kiro-directory.md#4-ステアリング--kirosteeringmd)

> **これは何か**: ステアリングは Markdown ファイルを通じて、**ワークスペースについての持続的な知識**を
> Kiro に与えます。**すべてのチャットで規約を説明する代わりに**、Kiro が確立されたパターン・
> ライブラリ・標準に一貫して従うようにします。

---

## 1. 何が良くなるか（公式の4点）

| 効果 | 内容 |
|------|------|
| **一貫したコード生成** | すべてのコンポーネント・API エンドポイント・テストがチームの確立したパターンと規約に従う |
| **繰り返しの削減** | **会話ごとにワークスペースの標準を説明する必要がない**。Kiro が好みを覚えている |
| **チームの足並みを揃える** | 新入りでもベテランでも、全員が同じ標準で作業する |
| **拡張可能なプロジェクト知識** | コードベースとともに育つ文書。プロジェクトの進展とともに決定とパターンを記録する |

---

## 2. 3つのスコープ

| スコープ | 場所 | 用途 |
|---------|------|------|
| **ワークスペース** | `.kiro/steering/` | **そのワークスペース固有**のパターン・ライブラリ・標準 |
| **グローバル** | `~/.kiro/steering/` | **すべてのワークスペース**に適用される規約 |
| **チーム** | `~/.kiro/steering/`（配布する） | **チーム全体**に適用する中央管理のステアリング |

### 2.1 チームステアリングの配布方法

**チームステアリングはグローバルステアリングの仕組みを使います。** 配布方法は2通りです。

| 方法 | 内容 |
|------|------|
| **押し込む** | **MDM ソリューションやグループポリシー**で利用者の PC に配布する |
| **取ってくる** | 利用者が**中央リポジトリからダウンロード**して `~/.kiro/steering` フォルダに置く |

組織での配布は [03_deployment/04_enterprise.md](../03_deployment/04_enterprise.md) も参照してください。

## 3. 基盤ステアリングファイル（3種を自動生成）

Kiro が用意する、プロジェクトの中核的な文脈を確立するためのファイルです。

| 順 | 操作 |
|----|------|
| 1 | Kiro パネルの **Steering** セクションへ移動する |
| 2 | **Generate Steering Docs** ボタンを押す（または **`+`** から **Foundation steering files** を選ぶ） |
| 3 | 3つのファイルが作られる |

| ファイル | 内容 | 効果 |
|---------|------|------|
| **`product.md`**（Product Overview） | 製品の目的・対象ユーザー・主要機能・ビジネス目標 | Kiro が技術的判断の**「なぜ」**を理解し、製品目標に沿った解決策を提案する |
| **`tech.md`**（Technology Stack） | 採用しているフレームワーク・ライブラリ・開発ツール・技術的制約 | Kiro が実装を提案するとき、**代替案よりも確立されたスタックを優先する** |
| **`structure.md`**（Project Structure） | ファイル構成・命名規約・import のパターン・アーキテクチャ上の決定 | 生成されたコードが**既存のコードベースに自然に収まる** |

**この3ファイルは既定ですべてのやり取りに含まれ**、Kiro のプロジェクト理解の土台（baseline）になります。

---

## 4. 自分でステアリングファイルを作る

| 順 | 操作 |
|----|------|
| 1 | Kiro パネルの **Steering** セクションへ移動する |
| 2 | **`+`** ボタンを押す |
| 3 | スコープを選ぶ（**ワークスペース**または**グローバル**） |
| 4 | 説明的なファイル名を選ぶ（例: `api-standards.md`） |
| 5 | 標準的な Markdown で指針を書く |
| 6 | 自然言語で要求を記述する |
| 7 | （ワークスペースの場合のみ）**Refine** ボタンで Kiro に要求を洗練させられる |

**作成すると即座に、すべての Kiro のやり取りで利用可能になります。**

## 5. 読み込みタイミング（inclusion modes・4種）

ファイル先頭の **YAML front matter** で指定します。

> ⚠️ **front matter はファイルの先頭に置かなければなりません。** 前に空行や内容を入れてはいけません（公式明記）。

### 5.1 `always`（常に含める・既定）

```yaml
---
inclusion: always
---
```

**すべてのやり取りに自動的に読み込まれます。**

**向くもの**: ワークスペース全体の標準・技術の好み・**セキュリティポリシー**・普遍的に適用されるコーディング規約。

### 5.2 `fileMatch`（条件付きで含める）

```yaml
---
inclusion: fileMatch
fileMatchPattern: "components/**/*.tsx"
---
```

**指定したパターンに一致するファイルを扱っているときだけ含まれます。** コンテキストを関連あるものに保ち、ノイズを減らせます。

**配列で複数指定**もできます。

```yaml
---
inclusion: fileMatch
fileMatchPattern: ["**/*.ts", "**/*.tsx", "**/tsconfig.*.json"]
---
```

**公式が挙げるパターン例**:

| パターン | 対象 |
|---------|------|
| `"*.tsx"` | React コンポーネントと JSX |
| `"app/api/**/*"` | API ルートとバックエンドのロジック |
| `"**/*.test.*"` | テストファイルとテストユーティリティ |
| `"src/components/**/*"` | コンポーネント固有の指針 |
| `"*.md"` | ドキュメント |
| `["**/*.ts", "**/*.tsx"]` | すべての TypeScript ファイル |

**向くもの**: 特定のファイル種別にのみ適用されるドメイン固有の標準（コンポーネントのパターン・API 設計の規則・テストの進め方・デプロイ手順）。

### 5.3 `manual`（手動で含める）

```yaml
---
inclusion: manual
---
```

**チャットで `#ステアリングファイル名` と参照したときだけ含まれます。** 必要なときだけ専門的な文脈を渡せます。

| 使い方 | 例 |
|-------|-----|
| コンテキストプロバイダとして | `#troubleshooting-guide`・`#performance-optimization` |
| **スラッシュコマンドとして** | チャットで **`/`** を打つと一覧から選べる |

> 🔑 **これが Kiro IDE のスラッシュコマンドの正体です。**
> **1.0 で manual トリガのフックが廃止され、この仕組みに置き換わりました。**
> 0.x で manual フックを使っていた場合、それらはステアリングファイルに移行されます
> （[02_update/03_migration-to-1.0.md](../02_update/03_migration-to-1.0.md)）。
>
> **Kiro CLI の固定スラッシュコマンド一覧を IDE に当てはめないでください。**
> IDE のスラッシュコマンドは**すべてユーザー定義**です（[00_information/README.md](../00_information/README.md#-ide-と-cli-を混同しないために)）。

**向くもの**: 専門的なワークフロー・トラブルシューティングのガイド・移行手順・**たまにしか必要ないコンテキストの重い文書**。

### 5.4 `auto`（説明に応じて自動で含める）

```yaml
---
inclusion: auto
name: api-design
description: REST API design patterns and conventions. Use when creating or modifying API endpoints.
---
```

**リクエストが `description` に一致したときに自動的に含まれます。** これは [Agent Skills](https://kiro.dev/docs/skills/) と似た仕組みで、**Kiro が `description` を見てそのファイルが関連するかを判断**します。

| フィールド | 必須 | 内容 |
|-----------|-----|------|
| **`name`** | **必須** | ステアリングファイルの識別子。表示と照合に使われる |
| **`description`** | **必須** | **いつこのファイルを含めるか**。Kiro がリクエストと照合する |

> **`auto` のステアリングファイルもスラッシュコマンドとして現れます。** `description` による自動的な
> 有効化に加えて、**`/` に続けてファイル名を打って明示的に含める**こともできます。

**向くもの**: 関連するときだけ読み込むべきコンテキストの重い指針（専門的なドメイン知識・複雑なワークフロー・常時読み込むと過剰になる詳細な参照資料）。

### 5.5 4種の使い分け

| モード | 読み込まれるとき | スラッシュコマンド |
|-------|--------------|----------------|
| **`always`**（既定） | 常に | — |
| **`fileMatch`** | 対象ファイルを扱っているとき | — |
| **`manual`** | **`#名前` で明示したとき** | ✅ |
| **`auto`** | **`description` がリクエストに一致したとき** | ✅ |

`manual` と `auto` の違いは「**自動で判断させるか、必ず明示するか**」です。

## 6. ファイル参照（`#[[file:...]]`）

**ワークスペースの実ファイルにリンクして、ステアリングを最新に保てます。**

```markdown
#[[file:<相対ファイル名>]]
```

**公式の例**:

| 用途 | 記述 |
|------|------|
| API 仕様 | `#[[file:api/openapi.yaml]]` |
| コンポーネントのパターン | `#[[file:components/ui/button.tsx]]` |
| 設定のテンプレート | `#[[file:.env.example]]` |

**ステアリングに内容をコピーするのではなく参照する**ことで、元ファイルの変更が自動的に反映されます。

## 7. `AGENTS.md` にも対応

Kiro は [AGENTS.md](https://agents.md/) 標準によるステアリング指示に対応しています。

| 項目 | 内容 |
|------|------|
| 置き場所 | **`~/.kiro/steering/`**（グローバルの場所）または**ワークスペースのルートフォルダ**。**1.0.288 以降は steering ディレクトリ内に置いた `AGENTS.md` も通常のステアリングとして読み込まれる** |
| 形式 | Markdown（Kiro のステアリングファイルと同様） |
| **inclusion modes** | ⚠️ **非対応。常に含まれる** |
| 設定 | **不要**（自動的に拾われる） |

**`AGENTS.md` では読み込みタイミングを制御できません。** 条件付きにしたい内容は Kiro のステアリングファイルとして書いてください。

### 7.1 ネストした `AGENTS.md`（1.0.309 で追加）

**サブディレクトリに `AGENTS.md` を置くと、ワークスペースの一部に限定した指示を Kiro に与えられます。** 例えば `services/api/AGENTS.md` と `packages/ui/AGENTS.md` を別々に置き、それぞれのコードに近い場所で指示を管理できます。

| 項目 | 内容 |
|------|------|
| 探索範囲 | ワークスペース全体のディレクトリツリー |
| 探索の除外 | **Git と Kiro の ignore ルールを尊重する**（`.gitignore`・`.kiroignore` に一致するディレクトリは探索されない） |
| 読み込み方法 | 他のステアリングファイルと同様、コンテキストに追加される |

> ⚠️ **公式ドキュメント間の食い違いに注意**（本サイトの調査結果）:
> 公式 [Steering](https://kiro.dev/docs/steering/) ページの「Agents.md」節（更新日 2026-08-12）は、
> サブディレクトリでの `AGENTS.md` 探索を **「On Kiro CLI」（Kiro CLI 限定）**と明記しています。
> 一方、公式 changelog の **1.0.309（IDE・2026-08-13）**は「ネストした `AGENTS.md` support」を**IDE の Improvements**として記載しています。
> **本ページは changelog の記述に従い、IDE でも利用できる機能として掲載しています**（changelog の方が新しく、IDE 版の変更履歴として明示的に記載されているため）。
> Steering ページ側の記述が更新されていない可能性があります。

## 8. 書き方のベストプラクティス（公式）

| 指針 | 内容 |
|------|------|
| **ファイルを絞る** | **1ファイル1ドメイン**（API 設計・テスト・デプロイ手順など） |
| **明確な名前を使う** | `api-rest-conventions.md`・`testing-unit-patterns.md`・`components-form-validation.md` |
| **文脈を含める** | **標準が何かだけでなく、なぜそう決めたかを説明する** |
| **例を示す** | コードスニペットや before/after の比較で標準を示す |
| ⚠️ **セキュリティ優先** | **API キー・パスワード・機密データを絶対に含めない。ステアリングファイルはコードベースの一部です** |
| **定期的に保守する** | スプリント計画やアーキテクチャ変更時に見直す／**構成変更後はファイル参照をテストする**／**ステアリングの変更もコード変更として扱いレビューを必須にする** |

## 9. よく作られるステアリングファイル（公式の例）

| ファイル | 内容 |
|---------|------|
| **`api-standards.md`** | REST の規約・エラー応答の形式・認証フロー・バージョニング戦略。エンドポイントの命名パターン・HTTP ステータスコードの使い方・リクエスト/レスポンスの例 |
| **`testing-standards.md`** | ユニットテストのパターン・統合テストの戦略・モックの方針・カバレッジの期待値。好むテストライブラリ・アサーションのスタイル・テストファイルの構成 |
| **`code-conventions.md`** | 命名パターン・ファイル構成・import の順序・アーキテクチャ上の決定。好むコード構造・コンポーネントのパターン・**避けるべきアンチパターン** |
| **`security-policies.md`** | 認証要件・データ検証規則・入力のサニタイズ標準・脆弱性の予防策。アプリ固有の安全なコーディング慣行 |
| **`deployment-workflow.md`** | ビルド手順・環境設定・デプロイ手順・ロールバック戦略。CI/CD パイプラインの詳細・環境ごとの要件 |
